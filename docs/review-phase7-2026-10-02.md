# Review after Phase 7 — October 2, 2026

The project now has a working small game-engine foundation: independent simulation, cameras, entities, shared model resources, retained render instances, physics, gameplay animation, saves, audio, inspection and device reconstruction. Its current boundaries are worth preserving. Further restructuring should isolate ownership and lifecycle responsibilities in small steps; moving the whole tree again would add migration cost without addressing the main remaining risks.

This review supersedes the earlier pre-migration reports. It examines the current 121 TypeScript source modules, dependency rules, public interfaces, asset preparation, persistence, hierarchy evaluation, resource lifetime, GPU phases, shaders, viewer/game integration, build scripts and existing tests. Automated architecture checks cover the source tree; behavioral checks cover the exercised paths. This does not establish full glTF conformance, exhaustive branch coverage or correctness on every browser/GPU.

## Contracts verified and retained

- Gameplay/physics owns entity roots; animation owns internal model hierarchy, with explicit per-instance overrides. Supported edits advance revisions and feed bounds, winding, uploads, shadows and occlusion dependencies.
- Immutable geometry, textures, materials, prepared clips and deformation inputs can be shared. Playback, pose, mutable compute outputs and visibility membership stay instance-specific.
- The renderer consumes already evaluated state. Pose upload precedes compute; compute precedes shadows and scene rendering; HDR composition precedes final tone mapping. Visibility never suppresses deformation or shadow updates based on stale readbacks.
- Material variants share the explicit slot layout and neutral defaults. Color slots use sRGB decoding; data slots remain linear. Texture transforms/UV selection, mip filtering and supported block compression remain covered by GPU fixtures.
- Transactional preparation and resource leases preserve active scenes after failed replacements. Retained world membership, slot reuse, device reconstruction and delayed visibility readbacks have integration coverage.
- Fixed simulation, animation checkpoints, prefab migration, component serialization, optional audio and inspection remain independent of renderer scheduling.

## Incremental refactoring order

Parts 1–4 are now implemented. Part 4 shares hierarchy primitives where validation semantics agree while keeping selection, full-model validation, expansion and entity subtree caches distinct; see [hierarchy primitives](hierarchy-primitives.md). Part 3 adds bounded CPU transport, metadata and payload validation before asset publication; see [asset validation and limits](asset-validation.md). Game bootstrap, restore, controls and presentation are separated under `game/session.ts`; see [the playable lifecycle](playable-slice.md). Part 1 lives in `renderer/core/device-resources.ts`. Device creation, scene transactions, release and private recovery candidates share one owner. The facade retains CPU recovery inputs and swaps a single GPU owner. Architecture and GPU lifecycle tests cover this separation; see [architecture](architecture.md) for the resulting ownership. The review verification counts above describe the original review; the subsequent refactor adds lifecycle regression coverage.

| Order | Change                                                                                                           | Completion criteria                                                                                                                                                                                                                                                                                    |
| ----- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1     | Extract device-owned state from `renderer/renderer.ts` into one lifecycle owner                                  | Construction, release and recovery swap one coherent resource owner; facade/camera identity and CPU playback survive. Keep initialization failure, lost-device retry, disposal cancellation and zero-live-byte tests passing. Avoid a render-graph abstraction unless dependencies actually demand it. |
| 2     | Split game bootstrap/session restore and presentation wiring out of `game/main.ts`                               | An application session owns input, runtime, tools, renderer and physics teardown. Restore/start failures have one cleanup path; storage failures cannot prevent a normal fresh launch. Keep gameplay systems free of DOM/storage.                                                                      |
| 3     | Tighten CPU asset validation/limits at the decoding boundary                                                     | Metadata is validated before allocation, errors identify the asset/path, and malformed inputs cannot corrupt a published world. Reuse the existing registry cancellation and transactional loading contracts.                                                                                          |
| 4     | Consolidate hierarchy primitives only where validation semantics agree                                           | Parent-first order, selected-scene membership, all-node pose validation and descendant expansion retain their distinct responsibilities. Explicit stacks are already implemented; share helpers only if doing so reduces real duplication without merging ownership.                                   |
| 5     | Separate cached world draw composition from membership/resource acquisition if world composition profiles poorly | Survivors keep handle/output identity; changes rebuild only affected CPU draw structures. Measure full-scene flattening/sorting before introducing persistent batch indexes.                                                                                                                           |
| 6     | Define editor commands and backend extension interfaces around actual content                                    | Components and assets remain versioned; undo/editing uses supported transforms and atomic membership APIs. Avoid replacing the component service with a full ECS before query/update costs justify it.                                                                                                 |

Checkpoint validation has already been extracted in this review: the controller drops from 506 to about 400 lines and keeps playback policy. Its checkpoint types are compatible through existing imports. At review time the renderer was the largest facade (709 lines); its device reconstruction ownership split is now implemented. Continue to use architecture checks to enforce acyclic CPU/GPU/viewer boundaries during that work.

The next milestone should use the completed device lifecycle cleanup with one representative game-content workload. That provides a concrete editor and performance target while keeping the working viewer and playable example usable throughout migration.

Refactoring part 5 is now implemented following a warm world-composition profile. CPU structural composition has a separate transactional cache; unaffected draw buckets/lists and per-model pipeline summaries are retained, while current bounds and frame scratch remain uncached. Membership/resource acquisition and commit-only uploads keep their existing ownership. See [measurements and cache contracts](world-composition.md) for before/after data and remaining O(N) work.
