# Project review — October 2, 2026

The renderer and engine foundation have useful boundaries and strong regression coverage. A complete rewrite is possible, but the next refactor should follow ownership and measured scaling costs. This review makes a concrete split between prepared model draw data and final scene bindings, fixes recoverable URL handling and buffer metadata validation, and preserves public APIs.

## Scope and findings fixed

The final source inventory contains 84 TypeScript modules across engine, glTF loading, animation, CPU scene state, renderer and viewer layers. Review focused on dependency boundaries, public APIs, preparation/replacement/disposal, mutable transform ownership, sparse animation, deformation batching, visibility/shadow dependencies, texture/material preparation, frame encoding and build/test configuration. Automated architecture checks inspect dependencies across the source tree. Behavioral tests execute the renderer's WGSL on WebGPU. This is a code review and regression run, not proof that every branch, asset or GPU implementation is correct.

For the eight-instance fixture, the old builder requested 1,024 bytes in per-model instance buffers plus the 1,024-byte world buffer: 2,048 bytes total. The old value is calculated from the prior allocation path; the new 1,024-byte request is instrumented in the GPU test. This saves half of **instance transform storage for this fixture**, not half of total GPU memory. Deformation outputs, textures and all other GPU allocations are excluded. Driver allocation granularity/residency are not measured.

The first full browser run overlapped source edits and had one viewer fixture failure. The affected viewer/world tests passed on the updated source; final validation uses a stable source snapshot. No performance claim is based on that overlapping run.

## Missing features and current limits

For an engine, entities/components are data and transform ownership is a writer policy; there is no implemented rigid-body simulation, collision/character controller, input-action system, gameplay system scheduler, audio, scripting, prefab/editor tooling or full runtime save-state framework. Add a small playable vertical slice before building all of those systems at once. A sensible first slice is an independently controlled camera and character, collision movement, and animation states feeding the existing renderer.

Animation supports independent playback, blending and explicit local overrides. Additive layers, per-node masks, root-motion extraction, retargeting, animation events and an IK solver remain opportunities. Overrides provide the integration point for IK but do not solve IK. Authored glTF root motion stays inside the model and does not currently move a physics-owned entity.

Asset/rendering opportunities include authored cameras/scene selection, material variants, additional material extensions, generated tangents and contextual unsupported-extension diagnostics. The supported extension list is explicit in `gltf/extensions.ts`; required unknown extensions reject rather than silently rendering a fallback.

Rendering limits remain: 32 punctual lights and four shadow lights; no directional cascades or clustered light assignment; fixed environment convolution quality; no LOD/resource streaming/indirect visibility path. Weighted transparency is approximate, and transmission uses an opaque background snapshot rather than complete multilayer refraction. Mip filtering lacks alpha-mask coverage preservation and normal-variance roughness correction. Device loss stops submissions but has no automatic recovery/reupload implementation. Anime rendering would additionally benefit from authored toon shading, outlines and artist-controlled lighting, with dedicated visual fixtures.

## Refactoring plan

Keep CPU loading/animation/engine code independent of GPU and viewer modules, shared `LoadedModel`/`ModelResources` separate from per-instance state, explicit fixed material/lighting layouts, and pose-upload → compute → shadow → color → presentation phases. Ownership tests and architecture cycle checks are useful constraints for every step.

1. Completed here: separate `SceneData` preparation from final instance storage/binding. This removes unused allocations and makes the world composition boundary clear.
2. Next: extract CPU world hierarchy evaluation into a cached iterative traversal, with meaningful deep/wide hierarchy tests and measurements.
3. Introduce persistent instance render handles and incremental scene assembly before adding streaming or a large ECS.
4. Separate camera inputs and simulation updates from rendering through adapters, preserving the viewer's default behavior.
5. Add typed inspection/validation surfaces before splitting the larger renderer/pose classes further. The largest source modules are renderer coordination (527 lines), pose evaluation (357), punctual lighting (300) and occlusion (286); size alone does not justify replacing them with many trivial classes.

Renaming every directory or rewriting existing passes would introduce compatibility risk without addressing the measured allocation issue or concrete engine gaps. The public API can evolve incrementally through these boundaries.
