# Code review — October 1, 2026

For the current engine/resource/transform audit, see the [October 2 follow-up](review-2026-10-02.md). This document preserves the earlier findings and verification results.

The project has a sound foundation and useful regression coverage. Asset decoding, CPU animation/poses, GPU preparation, pass encoding and browser controls already have distinct responsibilities. A second wholesale restructuring would mostly move files and destabilize internal imports. Focused changes to lifecycle handling, validation and frame coordination deliver more practical value.

This review inspected source modules, shaders, tests, decoder workers, build configuration and documentation, then ran CPU and real-WebGPU checks. It does not establish complete glTF conformance or performance across every GPU. Browser results below use the installed Microsoft Edge and available local WebGPU adapter.

## Issues fixed

| Finding                                                                                                  | Consequence before the fix                                                                                                               | Change and regression coverage                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Concurrent GPU preparation used independent validation scopes on the same device                         | Scene/environment scopes could overlap; a slower scene request could commit after a newer request                                        | New [`core/preparation.ts`](../src/renderer/core/preparation.ts) serializes preparation, validation and commitment per device. Unit tests cover scope order, GPU/CPU rejection recovery and independent devices. A WebGPU integration test overlaps scene and environment requests. |
| Animation notification exceptions escaped after scene assignment but before ownership handling completed | A throwing application callback could cause the newly attached scene's resources to be destroyed and leave previous resources unreleased | Scene commitment and previous-resource release now precede notification. The integration test throws from the callback and then renders the committed scene under GPU validation.                                                                                                   |
| Renderer construction happened outside initialization cleanup                                            | A failure configuring the canvas or constructing GPU subsystems could retain the device and previously prepared resources                | Constructor setup is inside the cleanup boundary; camera listeners attach after GPU setup. A browser test injects canvas configuration failure and verifies device destruction.                                                                                                     |
| Core material factors lacked the checks used for extension factors                                       | Malformed factors could reach shader uniforms, including out-of-range values, nonfinite numbers and incorrectly sized base colors        | [`materials/uniform.ts`](../src/renderer/materials/uniform.ts) validates core factors and boolean flags; `MaterialFactory` validates before decoding/uploading images. Tests retain valid negative normal scales and alpha cutoffs above one.                                       |
| Accessor stride and sparse count accepted fractional metadata                                            | Malformed assets could produce incorrect iteration or byte addressing instead of a useful diagnostic                                     | [`gltf/accessors.ts`](../src/gltf/accessors.ts) requires safe integers for these fields. CPU tests exercise both failures.                                                                                                                                                          |
| The frame loop handled exceptions only around part of preparation                                        | Resize, visibility and command-encoding failures could escape the renderer's error reporting                                             | Named `uploadFrame()` and `encodeFrame()` methods preserve the phase boundary; submission/scheduling handles errors from the complete frame.                                                                                                                                        |

Core factor ranges were checked against Khronos's [metallic/roughness schema](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/schema/material.pbrMetallicRoughness.schema.json), [material schema](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/schema/material.schema.json) and [normal texture schema](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/schema/material.normalTextureInfo.schema.json). Validation remains targeted; this change does not turn the loader into a complete schema validator.

## Highest-value improvements

These are implementation opportunities, not failures of the passing checks.

**October 2 follow-up:** the shadow-memory item below is now implemented. Lazy map capacity and a neutral binding preserve the fixed lighting layout; [measured before/after allocations](shadow-memory.md) and lifecycle regressions document the result. The table records the original October 1 recommendations.

The actual GPU texture-compression recommendation is also implemented: supported optional features negotiate retained BC7/ETC2/ASTC blocks with RGBA8 fallback. [Target selection, measured payloads and GPU coverage](texture-compression.md) document the change.

Occlusion now uses depth/receiver dependency invalidation, coherent result reuse and query suspension during continuous camera/occluder motion. [Before/after benchmarks and hierarchy investigation](occlusion-benchmark.md) explain the implementation and why a new depth-pyramid/indirect path is deferred.

## Missing or intentionally limited features

- **Asset coverage:** authored glTF cameras and additional scene selection; material variants; animation-pointer channels; material sheen, anisotropy, iridescence and dispersion. Compare additions with the [Khronos extension registry](https://github.com/KhronosGroup/glTF/blob/main/extensions/README.md), then implement validation and rendering together before accepting an extension as required.
- **Animation:** additive layers, per-node masks, root-motion extraction and retargeting. The separate controller/mixer/pose design is suitable for these additions; only the final mixed pose should drive upload revisions.
- **Lighting and presentation:** more scalable light assignment, cascaded directional shadows, more than four shadow-casting lights, configurable environment resolution, OpenEXR loading and additional tone curves. The current limits are 32 punctual light instances and four shadow lights.
- **Transparency and transmission:** weighted transparency remains approximate. Transmission samples an opaque screen snapshot, so nested glass and transparent geometry behind glass are not represented correctly. Exact layering/refraction requires a different rendering strategy and its own visual/performance tests.
- **Large scenes:** spatial acceleration, LOD selection, GPU-driven indirect draws and texture/resource budgets. Existing frustum, scale and asynchronous occlusion filters are useful foundations, but do not replace these capabilities.
- **Surface fidelity:** generated MikkTSpace tangents when absent, rather than relying solely on derivative bases. Authored tangents remain the best current route to matching baked normal maps.

Prioritize shadow/texture memory and measurements before expanding the feature matrix. For broader asset compatibility, authored cameras, material variants and selected material extensions are relatively clear next additions. For large-scene workloads, visibility and GPU memory matter more.

## Refactoring recommendation

The current structure follows the useful principle in [Toji's case study](https://toji.dev/webgpu-gltf-case-study/): prepare immutable state when loading and reuse it when drawing. Keep the existing CPU/GPU/application boundaries and explicit material binding contract.

Completed here: centralized device preparation transactions and extracted named frame phases. Both address concrete ownership/coordination problems without changing the public API. The upload phase still precedes compute, which precedes shadows and color rendering; immutable deformation inputs remain shared.

For a future refactor, use small independently verifiable steps:

1. Introduce a CPU asset-validation stage with contextual diagnostics, keeping decoded `Asset` independent of WebGPU.
2. Extract scene-preparation planning from `SceneBuilder` only when new resource budgets or features make it necessary. Separate validated descriptors from GPU allocation/commitment rather than creating many one-method classes.
3. Give renderer-owned allocations a consistent lifecycle/ownership helper as lazy shadow and compressed-texture resources are added.
4. Add typed browser-test inspection helpers so tests stop repeating internal casts and can follow module changes safely.
5. Split generated WGSL by material/lighting responsibility only where a block can be tested or reused; retain shared record definitions and the slot registry as the binding contract.

Keep public exports stable, run the existing architecture dependency tests after each step, and require pixel/compute regressions for behavior changes. The review does not recommend renaming every directory or replacing the renderer with a new framework.
